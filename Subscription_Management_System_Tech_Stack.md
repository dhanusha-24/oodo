# Subscription Management System — Final Technology Stack & Engineering Architecture

**Version:** 1.0 | **Date:** 31 October 2026 | **Status:** Implementation decision record  
**Companion document:** `Subscription_Management_System_Master_PRD.md`  
**Audience:** Senior developer, frontend/backend engineers, DevOps, QA, AI engineer

## 1. Final decision and implementation mandate

Build the product as a **React + TypeScript single-page web application**, a **Python FastAPI backend**, and **Google Gemini** for optional AI assistance. Use **PostgreSQL** for transactional data and **Redis + Celery** for scheduled work. All business-critical subscription, invoice, discount, payment, tax, and analytics calculations are deterministic Python/SQL code, **not Gemini outputs**.

This document **overrides only the technical-stack choices** in the Master PRD. All functional scope, roles, lifecycle rules, financial controls, and acceptance criteria in the PRD remain in force. Where the PRD contains competing technical examples, use the explicit conventions in this document.

## 3. System architecture

```text
Browser (React/Vite SPA)
    |
    | HTTPS, JSON, session cookie, CSRF token
    v
Reverse proxy / CDN
    |
    v
FastAPI (Python)
    |-- auth + RBAC + tenant boundary
    |-- customers / plans / subscriptions / quotations
    |-- invoice + tax + discount + payment services
    |-- analytics endpoints
    |-- Gemini AI gateway (optional, rate-limited)
    |
    +--> PostgreSQL (authoritative transactional data)
    +--> Redis (cache / queue broker)
    +--> S3-compatible storage (PDFs)
    +--> Celery workers + Celery Beat (billing / PDFs / email)
    +--> SMTP / transactional email provider
    +--> Google Gemini API (AI-only requests)
```

**Important:** React calls FastAPI, not PostgreSQL or Gemini directly. Workers call the same domain services as API routes. No background job should directly invent its own invoice-calculation logic.

## 6. Non-negotiable financial and state rules

1. Enforce `Draft → Quotation → Confirmed → Active → Closed` transitions in Python services, not just disabled UI buttons. Any exception/reopen flow must be separately authorized and audited as defined in the PRD.
2. Treat issued invoices as immutable; correct them through credit/reversal records, never silent edits.
3. Use **`Decimal` in Python and `NUMERIC` in PostgreSQL** for financial computation, with explicit currency precision and rounding. The canonical **public JSON API represents money as decimal strings** such as `"2124.00"` (as in the detailed PRD API section); do not mix minor-unit integers and decimal strings on different endpoints. Internal minor-unit conversion is permitted only in documented integrations.
4. Snapshot unit prices, discount parameters, tax rates and invoice line values at issuance. Changes to plans/taxes must not rewrite history.
5. Use `Idempotency-Key` for issuance, payment recording, allocation and state transitions; unique constraints must prevent duplicate billing periods.
6. Run invoice creation and payment allocation inside database transactions; use row locks/constraints to prevent oversubscription of discounts and over-allocation of payments.
7. All tenant-owned tables include `tenant_id`; every API query checks membership and tenant ownership. Never accept an arbitrary tenant ID as proof of authorization.
8. Store timestamps in UTC; keep tenant timezone and currency settings explicit. Billing dates use tenant-local calendar semantics.
9. Use a transactional outbox pattern for reliable notification/job dispatch after DB commits; workers must be retry-safe.
10. Do not represent an invoice as paid based on a Gemini response, frontend state, or unverified webhook.

## 7. Gemini AI — exact scope, limits and fallback

### 7.1 AI features included in v1

- **Explain dashboard:** Natural-language explanation of already-computed KPIs, including period, currency, filters and caveats.
- **Subscription insights:** Summarize trends from permission-filtered aggregates; flag possible overdue-payment patterns without claiming certainty.
- **Billing help assistant:** Explain what Draft/Quotation/Confirmed/Active/Closed mean, how invoices are calculated, and how discounts work, using approved product documentation.
- **Optional natural-language filters:** Convert a user's query into a restricted, validated filter object (e.g. `status=active`, date range); backend then executes predefined SQL, **never model-generated SQL**.

### 7.2 AI features explicitly forbidden

- Gemini must not set tax rates, calculate authoritative totals, create or modify invoices, authorize payments, transition subscriptions, override RBAC, run arbitrary SQL, or send customer communications without an approved deterministic workflow.
- Do not send payment credentials, passwords, secret keys, or unnecessary customer personal information to Gemini.

### 7.3 API implementation

- Python package: `google-genai`.
- Environment variables: `GEMINI_API_KEY`, `GEMINI_MODEL`, `AI_ENABLED=true|false`, `AI_MAX_REQUESTS_PER_USER_PER_DAY`, `AI_TIMEOUT_SECONDS`.
- Suggested endpoint: `POST /api/v1/ai/insights` with an allowlisted `insight_type`, filter object, and optional user question.
- Backend authenticates user, checks analytics permission, fetches tenant-scoped aggregated data, strips unnecessary identifiers, and sends the minimal context to Gemini.
- Validate structured AI outputs with Pydantic; label explanations **AI-generated**, and provide source metrics and calculation timestamps.
- Enforce timeouts, bounded tokens, per-user/per-tenant rate limits, concurrency limits and exponential backoff for transient failures; avoid retry storms.
- On quota exhaustion (`429`), model outage or disabled AI: show **“AI insights temporarily unavailable; core dashboard remains available.”** No billing workflow is blocked.

### 7.4 Free API key policy

Create a Google AI Studio key and select a **Gemini Flash-family model currently marked free-tier eligible** for the project's region and account. **Do not hard-code a specific model ID or promise unlimited free requests**: availability, quotas, region eligibility, data-handling terms and pricing change. At setup, check Google's official model/pricing/rate-limit documentation and set `GEMINI_MODEL` to the verified supported model. Configure spending controls where available and monitor quotas. A free key is suitable for prototype/demo traffic, not a guarantee of zero-cost production operation.

## 8. API and data contracts

- Base URL: `/api/v1` with OpenAPI-generated documentation at `/docs` in controlled environments.
- Use `GET/POST/PATCH` REST conventions and stable response schemas; pagination defaults to 25 and caps at 100.
- Send UTC ISO-8601 timestamps, ISO-4217 currency codes, and **decimal strings for all monetary JSON fields**.
- Error format: `{ "error": { "code": "INVOICE_ALREADY_ISSUED", "message": "...", "details": {} }, "request_id": "..." }`.
- Implement `/auth`, `/tenants`, `/users`, `/customers`, `/plans`, `/subscriptions`, `/quotations`, `/discounts`, `/invoices`, `/payments`, `/analytics`, `/notifications`, `/settings`, `/audit`, and `/ai/insights` route groups according to the Master PRD.
- Generate TypeScript types from the FastAPI OpenAPI spec during CI; fail builds on breaking undocumented schema changes.
- Document role permissions, transaction boundaries, request idempotency and audit effects per mutating route.

## 9. Security decisions

- Use server-side opaque session IDs in `Secure`, `HttpOnly`, `SameSite=Lax` cookies; implement CSRF token validation for unsafe requests. Prefer same-site frontend/API hosting to simplify cookie policy.
- Argon2id password hashes, login throttling, account recovery with expiring one-use tokens, session revocation and secure reset flows.
- Authorization in each backend service, not only in React route guards. Audit privilege changes.
- Validate and sanitize all input; parameterized SQLAlchemy queries; strict CORS allowlist; safe PDF template escaping; secure signed object downloads.
- Never expose `GEMINI_API_KEY` or database credentials to React, logs, error messages or Git.
- Encrypt data in transit, use encrypted managed storage/backups, and define retention/deletion policies before live launch.
- Audit AI usage metadata without storing unnecessary sensitive text.

## 10. Performance plan (<2 seconds)

**Acceptance workload:** at least **10,000 subscriptions, 100,000 invoices, 200,000 allocations per tenant and 100 concurrent users**. Measure p95 ordinary API list/detail/dashboard responses under 2 seconds in staging; exclude external Gemini latency and asynchronous PDF generation from this API-specific SLA. Frontend perceived page performance should be separately measured with realistic network profiles.

- Index `tenant_id` + frequently filtered/sorted fields; unique invoice billing-period keys; index foreign keys.
- Use server pagination, stable cursor pagination for deep lists, debounced search and targeted SQL projections.
- Avoid N+1 queries via SQLAlchemy eager-loading/explicit joins; use PostgreSQL `EXPLAIN ANALYZE`.
- Cache safe aggregate analytics in Redis with event-driven invalidation or short TTL; never share cached tenant data across tenants.
- Offload PDFs, scheduled billing, emails, exports and heavy summaries to Celery.
- Use connection pooling, request timeouts, efficient serialization, Vite route-level code splitting and chart lazy loading.
- Test with Locust and instrument FastAPI/SQL/Celery. Correct bottlenecks before increasing hardware.

## 12. Development and deployment sequence

1. **Foundation:** monorepo, Docker Compose (Postgres, Redis, MinIO, Mailpit), React/Vite app, FastAPI app, migrations, CI, session auth, tenant RBAC.
2. **Core catalog:** customers, plans, versioned pricing, settings, searchable paginated tables.
3. **Lifecycle:** drafts, quotations, acceptance, confirmation, activation, closure, state audit and permissions.
4. **Finance:** tax/discount engine, billing periods, invoice PDFs, Celery schedules, payments, allocations, reversals and reconciliation.
5. **Insights:** deterministic analytics, overdue reports, exports, cache invalidation and permission checks.
6. **Gemini:** optional AI insights, controlled filters, validation, free-tier rate-limit handling and fallback.
7. **Hardening:** integration/E2E/security/load tests, monitoring, backups, disaster recovery rehearsal, deployment and documentation.

### Minimum release gate

- Every acceptance scenario in the Master PRD passes.
- No cross-tenant access; no duplicate invoice issuance under concurrent workers; financial totals reconcile.
- Core product works with `AI_ENABLED=false` and with Gemini returning 429 or timeout.
- Normal list/detail/dashboard p95 API latency <2s at defined seeded workload.
- All migrations, backup/restore, startup checks, error monitoring and CI checks pass.
- Production tax policy, email sending domain, hosting region, data handling, retention and payment integration scope have explicit owner sign-off.

## 13. Technical choices intentionally excluded

| Do not use | Reason |
|---|---|
| Next.js as the frontend framework | User chose React SPA; Vite keeps frontend separate from Python backend |
| NestJS / Node.js for backend business logic | Backend must be Python FastAPI |
| Prisma as Python ORM | SQLAlchemy + Alembic is the chosen Python-native data layer |
| BullMQ | Celery + Redis is the chosen Python-native job architecture |
| Firebase/Firestore as primary database | Financial data needs PostgreSQL transactions and relational constraints |
| Gemini SDK in the browser | Would expose API key and bypass authorization |
| Gemini for authoritative finance | LLM outputs are nondeterministic and must not control financial records |
| Client-only access controls | All permission checks must be server enforced |

## 14. Handoff instruction to senior developer

Implement this stack exactly unless an engineering constraint is documented in an Architecture Decision Record and approved. Treat the Master PRD as the source of truth for **what** the system must do, and this document as the source of truth for **how it is implemented**. Produce a working integrated product, not static mock screens. Ensure that the app remains fully functional without AI; Gemini adds optional explanations and insights only. Record any unresolved jurisdiction-specific production configuration as a launch blocker rather than guessing legal requirements.
